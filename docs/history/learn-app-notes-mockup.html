Class notes: what a session becomes afterwards

TA is built. Every session now leaves a file: your notes in order, each with the TA's replies threaded under it, the checks, the deeper passes, the widgets. This page is about what that file turns into — the thing you go back to, and mine for posts. Three forms, the same real content in each, a recommendation, and the two questions you asked alongside: which OSS models, and how notes should be stored.

The content below is from tonight's dry run of the real desk, with the mock model; the replies read as the brain notes because that is what the mock returns. Live replies will be composed, not copied.

TA · Knowledge in weights vs knowledge in context

Your phone keyboard has no list of your sentences in it. It has a pile of numbers that were nudged, over millions of messages, until its guesses got good. Type “I’ll be there in five” and it offers “minutes” — not because “minutes” is filed anywhere, but because the numbers came out that way. An LLM is the same trick at scale.

51:281:39:43

TA · deeper · unchanged

Training left the weights in a shape that makes true-ish continuations more likely than false ones — Karpathy calls it a lossy compression of the internet. That is why a wrong answer arrives in the same confident voice as a right one: there is no lookup that could miss.

27:00

Temperature = how much tolerance we have with the probability. low temperature = higher accuracy #til

Check this

“low temperature = higher accuracy”

Low temperature makes it repeatable, not right. At 0 it always takes its top candidate — so if the top one is wrong, you get that same wrong answer every single time, and with more confidence. Accuracy comes from the weights and the context; temperature only decides how far down the list it is willing to reach.

Knowledge in weights vs knowledge in context · c-knowledge-in-weights

Lecture“it’s all just a vague recollection of Internet documents” · 51:28
You asked“a lot of the world knowledge is stored in the parameters” — what? how?
AnswerNothing is stored and looked up. The weights are a lossy compression that makes true-ish continuations likely; context is what it can actually read.
The thing to remember

Weights are what the model half-remembers; the context window is what is in front of it. Temperature changes neither — it only changes how adventurous the coin is.

Strength

Blog-ready. The keep block is what a brain post wants. Searchable by concept across every session you ever have.

Weakness

Loses the order you learned things in, and the digest itself is model-written — one more place where the generator can go generic on you. This is the "article" failure mode wearing a nicer coat.

Recommendation

B is the document, C is its index, and it is rendered twice

  • The threaded notebook is the record. It is a pure rendering of the session file — no generation, no chance of drift — and it is in your voice. Chronology is the thing you cannot reconstruct later, so it is the spine.
  • The concept digest sits on top as an index, one block per concept touched, linking down into the threads. This is the only generated part, and it is short: the “What’s right” line is the check’s correction, the “Answer” line is the reply’s first two sentences. Nothing is summarised across sessions; each concept block points at where it happened.
  • Two renderings from one file. A Claude artifact for the living version: widgets run, native comment threads work, you can keep poking. And a brain post for the keep-forever version: the same notebook and index as plain HTML, widgets as a still with a link to the artifact.
  • One rule of yours is in the way. Your blog at brain.kaushikbhat.com has a rule you set on 5 Sept: posts are plain HTML, no JavaScript, no comment layer. The class notes have widgets, and widgets are JavaScript. That is why the notes are a Claude artifact first, and the blog would get a copy with stills. Question 2 below is whether you want to keep that rule or change it.
  • Not a new build. The renderer is one script reading sessions/*.json. The artifact rendering reuses the sidebar’s CSS and the widget runtime; the brain rendering uses post.css via the existing post template.

Models

OSS models for the TA, via OpenRouter

Picked tonight from the live OpenRouter catalogue (430 models) by price, context length, and the reasoning/tools flags, plus what the family is known for. Honest caveat: I have not run them. npm run bench pushes your six real Milestone 1 doubts and four real notes through any list of candidates and prints the replies, so the pick can be made on evidence. Every job is overridable from the Pages environment without touching code.

Storage

Where notes live, and the better idea

What is built tonight, and the alternatives I weighed.

LayerWhatWhy
Local firstbrowser.storage.local · s:<videoId>A jot lands instantly and works offline. The panel renders identically with the desk down. Optimistic first, per the invariants.
Live copyKV · note:<src>:<id> written by the extension · reply:<src>:<id>:<seq> written by the deskOne writer per key, so two devices never fight. A check that finds nothing is not stored — absence is the record. Same architecture as every other app here.
Durable copysessions/<videoId>/<date>.json in the repo, via npm run exportThe better idea. KV is a cache; the file is the archive — diffable, greppable, and the single input to the class-notes renderer. A session is done when its file is committed.

Considered and not done. D1 (SQLite): queryable across sessions, but it breaks the standing KV-only constraint for a benefit the exported files already give you with grep. The tracker artifact’s db: it is right there, but the brief’s hard boundary says no, and the invariants say couplings are one-way and narrow — the clipboard digest is that coupling. Git-only, no KV: tempting, but then the panel cannot see replies from another device until you export and pull; KV is what makes the sidebar work on the phone next to the laptop.
